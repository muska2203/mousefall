# Mousefall — Roadmap крупными мазками

> Черновик плана на ревью.  
> Цель: из текущего прототипа с 10 одинаковыми уровнями сделать полноценный 10-этажный roguelike.

---

## Видение

- **10 этажей**, каждый — уникальный биом с собственными пулами врагов, предметов и боссов.
- **Босс на каждом этаже**: случайный из пула этого этажа/биома. Переход на следующий этаж — только после его убийства.
- **Прокачка внутри забега**: через предметы — заменяемая экипировка + накапливаемые реликвии. Реликвия выбирается (1 из 3) на алтаре выбора в начале каждого этажа. Классического XP/level-up нет. См. [`docs/game-design/progression-concept.md`](./docs/game-design/progression-concept.md).
- **Экономика**: золото с врагов/сундуков/боссов, магазин между этажами, возможный крафт/улучшение снаряжения.
- **Мета-прогрессия**: нет. Сейчас — «трушный рогалик».
- **UI/анимации и сохранения**: в последнюю очередь, после стабилизации игрового цикла.

## Этап 0. Прогрессия: реликвии и алтарь выбора

> **Статус: выполнен (2026-08-06).** Реализация по плану [`docs/plans/stage-0-relics-altar.md`](./docs/plans/stage-0-relics-altar.md) (все фазы + финальное ревью); критерий готовности подтверждён полным прогоном проверок.
>
> Цель: система прокачки внутри забега реализована по [`docs/game-design/progression-concept.md`](./docs/game-design/progression-concept.md) **до** работы над контентом этажей — баланс и контент этапов 1+ сразу проектируются под реликвии.

### 0.1 Удаление XP-задела
- Удалить «проводку» XP (механики начисления не существовало): поля `xp`/`level` игрока, `xpReward` (схема + шаблоны врагов), `XP_PER_LEVEL`, событие `PLAYER_LEVELED_UP`, `source: 'levelup'`, xp-бар и бейдж уровня в UI, связанные i18n-ключи и стили. Полный объём — вопрос №5 концепта прогрессии.
- Не трогать уровни способностей (`grantedAbilities[].level`, формулы урона скиллов) — это отдельный задел.
- Отдельным коммитом; после удаления — запись в `docs/agents/SYNC_STATUS.md`.

### 0.2 Контентный тип «реликвия»
- Схема, загрузчик, реестр, тексты ru/en, валидация: `ruleIds`, `statModifiers`, `stackable` (обычные стакаются, уникальные — одна на забег), опционально `grantedAbilities` (возможность закладывается, в MVP пуле не используется).
- Получение реликвии → регистрация правил в `activeRules` по образцу экипировки; семантика стаков: модификаторы суммируются, правила не конфликтуют по `source`.
- Технический лимит коллекции — константа (символически 100).

### 0.3 UI коллекции реликвий
- Панель по образцу `SkillsPanel`: иконки, поповеры, отображение стаков.

### 0.4 Спавн poi в генераторе этажей
- Пул poi в `MapParams` (по образцу `itemPool` / `enemyPool`).
- Гарантированное размещение алтаря выбора рядом со спавном игрока на каждом этаже.

### 0.5 Алтарь выбора реликвии
- Новый poi «алтарь выбора». При **первой** активации генерирует предложение из 3 реликвий пула этажа (`relicPool` по образцу `itemPool`) и хранит его в состоянии poi (входит в снапшот этажа).
- Модальное окно выбора 1 из 3; отказ закрывает окно — алтарь остаётся активным, предложение не меняется.
- `charges` тратится только на взятие реликвии; состояние «использован» — через `spriteVariants`.
- Уникальные реликвии, уже имеющиеся у игрока, исключаются из генерации предложений.

### 0.6 Стартовый пул реликвий
- Набор реликвий под существующую выразительность DSL правил (без расширения DSL).
- Пулы реликвий по этажам в шаблонах карт.

**Критерий готовности:** на каждом этаже у старта стоит алтарь выбора; выбор 1 из 3 работает (включая отказ и повторное открытие с тем же предложением); взятая реликвия регистрирует правила/модификаторы и видна в панели; XP-задел удалён; тесты изменённых областей и `npm run typecheck` зелёные.

## Вопросы по механикам — решить до начала этапа 1

> Отчёт по текущим механикам: [`docs/game-design/mechanics-overview.md`](./docs/game-design/mechanics-overview.md) (раздел 10 «Пробелы»). Эти решения влияют на дизайн босса, баланс первого этажа и контент расходников; проработать их можно параллельно с этапом 0, но стартовать этап 1 без ответов нельзя.

1. **Боевые роллы.** ~~Уклонение/точность/крит рассчитываются, но в бою не используются — попадание всегда точное (§10.1).~~ **Решено (2026-08-04):** фиксируем «всегда попадание» — бинарных роллов попадания/уклонения нет. `accuracy`, `dodgeChance`, `critChance` и событие `ENTITY_MISSED` выпиливаются по образцу XP-задела (этап 0.1, отдельным коммитом). Крит — детерминированный по условию, `critMultiplier` остаётся статом; стартовое условие для этапа 1 — удар по цели со статусом `dazed`/`stunned`; набор условий крита расширяется контентом по мере появления новых механик (например, `wet` + электричество). Статусы накладываются детерминированно (тип урона / состояние цели), а не по шансу: `weapon_poison_on_hit` и `weapon_blunt_daze` переводятся с вероятности на «всегда»; баланс значений/длительностей и иммунитеты врагов — проход в рамках этапа 1.4. 2. **DSL под механики босса.** ~~Щит и парирование Кота-Стража (1.3) упираются в ограничения правил (§10.4: условия не работают с `modifyDamage`, нет эффектов «блок щитом»). Проверка кода показала, что ограничение из §10.4 устарело: условия работают с `modifyDamage` (`apply-intent-modifiers.ts`, есть тест), правила привязываются к врагу через экипировку и статусы (`rebuildActiveRules`). Единственная доработка — обобщённый исполнитель self-buff способности (`statusType`/`duration` из шаблона способности) вместо захардкоженного `counterattackSkill`. Семантика `multiply 0` против «минимум 1 урона» закрывается тестом при реализации. Конкретный вариант щита (пассивное снижение / периодическая стойка / оба) определяется при дизайне босса в п. 1.3.
3. **Боссы как контент.** ~~Список боссов захардкожен (§10.5) — нужен флаг `isBoss` в шаблоне; условие перехода «убийство босса открывает лестницу» не реализовано.~~ **Решено (2026-08-04):** флаг `isBoss` в шаблоне сущности заменяет захардкоженный `BOSS_TEMPLATE_IDS`; экран концовки переводится на имена боссов из контента. Пул боссов — `bossPool` в `MapParams` (по образцу `enemyPool`/`itemPool`), генератор гарантированно размещает случайного босса из пула. Гейт перехода — **босс-комната** (не печать лестницы): генератор помечает дальнюю от спавна комнату босс-комнатой и строит за ней комнату награды, достижимую только через босс-комнату; в комнате награды — лестница вниз и ключевые объекты (MVP: алтарь лечения; до реализации сундуков награда — отдельный пул лута босса). Двери босс-комнаты — особый шаблон: неразрушаемые, негорючие, с новым универсальным состоянием двери «заперта». Логика: игрок вошёл в босс-комнату → двери закрываются и запираются (триггер — сам факт входа в комнату, безусловно, независимо от агро босса); все боссы комнаты мертвы → отпираются насовсем; игрок любым способом вышел до победы → отпираются, при этом урон боссу **сохраняется** (без сброса HP), а босс выходит из комнаты и **преследует** игрока (анти-эксплойт «ударил-сбежал» + тактика заманивания в ловушки). Отложенная доработка триггера: перевести закрытие на «рычаг» — двери закрывает босс, когда видит игрока; этот же рычаг может дёрнуть игрок, чтобы снова открыть двери. Требование к генератору: сохранять границы и типы комнат в состояние этажа (универсально — пригодится для магазинов и особых комнат).

Стартовый набор типов этажа 1: `start` (алтарь выбора реликвии), `normal` (обычные враги, лут, колючки по пулам), `elite` (сильные враги, бочки с маслом, повышенная награда), `boss` (босс + запирающиеся двери, см. вопрос №3), `reward` (лестница + алтарь лечения + пул лута босса). Отложено: тип `rest`, модификаторы комнат («случайные дополнительные условия» — вариант 2), префабы комнат (вариант 3), не-floor террейн (песок) с учётом `moveCost` в AI/автопути.

## Этап 1. Первый этаж + первый босс

> Цель: есть работающий вертикальный срез — один полноценный этаж с боссом, который можно пройти.

### 1.1 Скиллы стартового снаряжения (Перед этим доработать эги в оружии. Переделать тип урона под тэги)
> Цель: у каждого вида начального снаряжения есть осмысленный выбор из 2 активных скиллов.

- Создать 2 скилла для оружия (например, сильный удар и серия ударов).
- Создать 2 скилла для брони (например, блок и контратака).
- Создать 2 скилла для амулета (например, лечение и бафф).
- Оформить все скиллы как `AbilityTemplate` и привязать к стартовым предметам через `grantedAbilities`.
- Проверить, что скиллы корректно выдаются при старте забега и отображаются в панели скиллов.

### 1.2 Генерация и параметры первого этажа
- Задать `MapParams` для 1-го этажа: размер, плотность врагов, плотность предметов.
- Определить визуальный стиль/биом первого этажа.
- Спавн врагов и предметов по пулю для 1-го этажа.

### 1.3 Первый босс — Кот-Страж
- **Концепция:** тяжеловооружённый босс-первого этажа, обучающий игрока механике щита и парирования.
- **Механики:**
  - **Щит:** пассивное снижение входящего урона или периодическое активирование неуязвимости.
  - **Парирование:** при получении удара в определённом состоянии наносит ответный урон.
  - **Тяжёлая броня:** высокое здоровье и броня, низкая скорость.
- Расширить схему контента под боссов (isBoss, награды).
- Генерация босса на этаже.
- Условие перехода: убийство босса открывает/появляет лестницу.
- Босс-комната, комната награды и запирающиеся двери — по решению вопроса №3 (раздел «Вопросы по механикам» выше).

### 1.4 Базовый контент 1-го этажа
- Пул врагов для 1-го этажа (можно на основе текущих + 1 новый).
- Пул предметов для 1-го этажа.
- Базовые расходники (лечение, баффы).
- Слияние стопок при подборе (до `maxStack`) + валидация «`stackable` несовместим с `abilityPool`» — по решению вопроса №5.

### 1.5 Условие победы в забеге
- После убийства босса 1-го этажа — переход на следующий этаж (заглушка/тот же биом допустим на этом этапе).
- Финальная победа временно = прохождение 1-го этажа.

**Критерий готовности:** можно начать забег и пройти 1 этаж, убив босса.

> Цель: итого 3 рабочих этажа с разными биомами/врагами/боссами.

### 3.1 Этажи 2 и 3
